# 我为什么放弃多 Agent 工作流

这段时间看了不少"AI 工作流"的内容，一种很流行的做法是：把一个写文案的活，拆成"策划 Agent → 写作 Agent → 润色 Agent → 审核 Agent"，好像角色越多就越智能。我试下来发现，大部分是花架子。

真正让我想通的，不是某个教程，而是我自己搭一套系统时的取舍。今天我把"记录 → 写作 → 发布"和"服务监控"两条链路都搭完了，全程只用了很克制的 AI 角色。这篇讲讲我为什么这么收敛。

## 多 Agent 真正贵在哪

每个 Agent 都要重新加载指令、把背景上下文灌进去一遍，结果再汇总回主控。这些是重复开销。任务越碎，"搬运费"占比越高。

但浪费不是绝对的。任务能真正并行、且互相独立时，多 Agent 反而省——比如同时查十份资料，拆出去各查各的，最后只汇总结论，避免主会话上下文越滚越大。需要隔离上下文时也值：一个长文档分析拆给子 Agent，不会撑爆主会话。

判断标准就一条：拆开之后，每个子任务是不是真的独立、有没有各自的上下文需求？如果拆完大家看的还是同一份材料、干的还是同一件事，那就是纯表演，单 Agent 一把梭更划算。

## 落地案例一：服务监控，我让 AI 只当"被通知的人"

我的服务器只有 1.6G 内存，跑着两个 Java 服务和一个静态博客，装不下 Uptime Kuma 这类监控面板。第一反应可能是在上面再跑几个 Agent 盯着，但我没有。

最终方案：一个探活脚本每十分钟访问三个公网地址，全绿就静默，有服务挂了就退出码 1。探到异常时，OpenClaw 才被唤醒——自动 SSH 上服务器查 `systemctl status` 和 `journalctl`，把"哪个服务挂了、可能原因、建议"发到微信。

关键点：**监控的采集是脚本做的，不是 AI。** AI 只做"收到告警后判断该看什么、怎么解释"。这样平时零 token 消耗，只在出事时才动用智能，响应也快一个数量级。

## 落地案例二：部署，交给 CI 而不是 Agent

博客是 Astro 静态站。以前发文章要手动 SSH 上传，现在用 GitHub Actions：push 到 main 分支，自动构建、SSH 上传、原子切换服务器目录。整个发布是确定性的，构建绿了就上线，红了就失败，没有中间地带。

这一步我没让任何 Agent 掺和。部署是"规则明确、可验证"的活，交给工具比交给 AI 可靠得多。AI 在这里唯一的角色，是在构建失败时读日志、定位原因。

## 落地案例三：写作工作流，AI 做整理不做决策

写作这块我反而让 AI 参与得多一点，但边界很清晰。日常记录随手追加进日志文件（几乎零成本），只有当我明确说"整理成文"时，AI 才把零散日志提炼成结构化草稿。写作本身是我的活，AI 只帮忙把素材从碎片变成提纲。

这条链是：想到什么十秒钟记下来 → 定期让 AI 整理成草稿 → 我在编辑器里打磨 → push 自动上线。

## 我最后收敛成的样子

不再追求"几个角色开会"，而是明确分工：

- **一个总控**：接收告警、收集信息、决定下一步找谁。
- **一个修代码的**：只有代码真的需要改时才叫它，干完就退出。
- **一个分析模型**：读日志、总结错误、判断问题原因。

最重、最确定的活，交给传统工具：部署给 CI，监控采集给探活脚本，AI 只做决策和解读。

## 效果

这套跑起来之后，AI 的角色回归到它该在的位置：记录、整理、改写、发布，而不是掌控整个系统。想到东西十秒钟能记下来，想发博客几分钟能整理，代码 push 后自己上线。这比再加五个 AI Agent 提升大得多。

我至今没搞 CEO Agent，也没上十几个角色。原因很简单：那些是表演，而我要的是能把一件事真正做完的系统。
